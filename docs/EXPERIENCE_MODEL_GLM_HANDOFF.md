# memory-mcp 经验召回与热融合实施方案

给 GLM 实现与验收使用 · 2026-11-20 · 设计稿

## 1. 背景和交付目标

维护者希望把自己使用经验的方式蒸馏成一件通用工具。人遇到错误、修过 bug、学到现场业务知识之后，下次遇到相似情形，会想起相关经历，再拿它与眼前的情况对照。有时因此发现风险，有时能放心地继续原任务。工具要迁移的是这种判断能力。用户少纠正一次、Agent 在本应直接完成时少打扰一次，都有价值。

2026-11-19 的 ZCode/GLM 复盘给出了四种必须同时解释的现象：

| 案例 | 对设计的约束 |
| --- | --- |
| 结算编码由线下系统按环境配置。维护者确认，现有经验召回曾使 Agent 在需要时考虑环境差异。 | 保留现有数据词触发路径。业务事实可以来自代码以外；“可能不同”不能被改写为“必然不同”。 |
| wrong-row 案中，包含定位错行风险的正文已经到场。Agent 考虑了跨环境差异，仍把局部项当成整屋目标，错误 SQL 经回复正文交付。 | 投递成功、注意到一个风险、最终选对对象，必须分别验收。工具 hook 可能看不到实际交付物。 |
| 工作区读取被写成“master 实测”；库中还有标题断言已恢复、正文保留“未提交未推送”限定的案例。 | 核对证据实际观察的对象。标题和短提醒均可能越过正文能支持的断言。 |
| 用户两次直接指出交付物有问题后，Agent 作出修正。 | 值得试验交接前的定向挑战。人工纠偏含有新的判断或指向；机器以中性问题能否复现这一效果，仍须盲测。 |

GLM 把部分情形称为 A 类“填开放位置”、C 类“重审已有判断”。它们描述的是**一次经验与一次任务的关系**。同一条经验在选值前和写定值后可能呈现两种关系。当天报告的 4/4、0/1 和人工纠偏 2/2 是案例观察，不能作为跨任务成功率或自动挑战的验收成绩。

## 2. 两个核心函数

**召回函数** `R(x, M) → 候选经验及来源`。输入是项目范围、可观察线索或宿主主动构造的查询，以及当时的索引版本。它回答“这让我想起什么”。确定性在这一层要求：相同的规范化输入、库快照和投递状态，应能回放出相同的候选与投递行为。

**热融合函数** `F(j, E, m) → 当前判断或动作`。输入是准备作出或已写在草稿中的判断 `j`、本次证据 `E`、被唤起的经验 `m`。宿主负责判断历史与当前的关系。输出可以是维持、补充、收窄或修正判断，也可以是取得一项能影响交付的缺失证据。

动态参数 `P` 表示本次对照值得投入多少核查。它在 F 内部产生。若把历史中容易混淆的两种情况互换，本步答案或作用对象仍一样，或当前证据已解决这个区别，就直接继续。若结论会改变且证据尚未区分，临近交付时核查或收窄；证据已反驳草稿时直接纠正。无需 LLM 报小数，也无需先自觉“有风险”才能收到经验。

机制保证候选、路由和收据可以复核。热融合的成效从最终交付和实际操作测量；不读私有推理，不用“我已思考”的表态代替结果。

## 3. 写入协议与兼容性

沿用同步的 `memory_experience_record`。先修当前任务。纯文字误读、一次性进度或只有“下次仔细点”的感想，修正后结束。沿用已有 `admission.future_decision` 和 `admission.evidence_ref`，让作者指出下次能多区分什么，并引用本次提交的证据。admission 只在写入边界使用。

**建议的输入契约**：同一工具支持下面两种正文形态。字段名可随现有协议约定调整，但语义、互斥校验及旧数据兼容需保留。

| 正文形态 | 内容 | 适用例 |
| --- | --- | --- |
| `counterexample` | `pitfall` 写当时哪一步推断失效，`counterexample` 写推翻它的观察。 | “把工作区输出当作目标分支的读取结果”；反例须指向当时真实读取的对象和复核依据。 |
| `fact` | 一条有来源、会改变具体判断的业务事实。保留对象、环境或时间等必要限定。 | “结算编码由各环境的线下结算系统分别配置。”没有观察到值不同时，也可以凭来源记录配置归属。 |

两种形态都需要紧凑证据定位、已举证的 cue 关联，以及可复用的判断。代码引用可核查实际路径、符号和版本，业务引用可以是受认可的配置记录或维护者确认的来源。引用存在只能验证定位，语义由宿主负责。已经明确确认的项目约定沿用现有 `memory_reference_record` 及其权威来源、适用范围和例外语义。普通业务事实不得借此升级为指令。当前任务要求、现行项目约定和本次可核实的事实优先。

新经验停止要求逐栏填写 `impact`、`applicability`、`boundary`。对反例成立有用的限定直接写进事实本身。cue 保留稳定 ID、可识别的匹配入口和证据引用；取消经验侧独立撰写的 `cue.text`。标题可作导航；自动投递的事实只来自正文与定位。检查首个 lookup、新关联短提醒、旧摘录和证据备注，避免旁路把已删除的结论送回上下文。

**旧库处理**。先在副本上完整盘点，并追踪哪些旧记录的必要限定只存在于被裁掉的字段。能无损展示的走精简投影；有歧义的保留原始记录和可追溯标记，在按原始证据核实前保留限定，不悄悄发布截短后的强断言。缺少证据时报告待人工核实的条目。无需凭旧正文批量生成新的业务事实。实质改变走现有修订机制；入口别名、投递去重和旧请求重试分别验证。共享 cue 类型的约定工具单独回归。协议不兼容时走已有版本及备份升级流程，保留可回退基线。

旧客户端若继续提交带叙述字段的写入请求，按声明的协议版本兼容处理，或返回带字段位置的升级提示。不得先丢弃这些字段再返回写入成功。无论走哪条路径，重试、失败和并发都不能留下半条记录、孤立的 cue 或误记的成功收据。

## 4. 召回与前置热融合

保留现有项目绑定、匹配、主动 lookup、分页和上下文代际收据。同一经验版本的正文尚未送达时，沿用命中索引后 lookup 的路径；收到原生成功结果后才记对应条目和关联已交付。送达后仅新关联给一次该版本已有的短事实或反例，同关联静默。短提醒须包含完整限定，预算不足时保留获取完整事实的入口。风险不为无关条目增加匹配权重。

下列常驻提示由宿主使用。历史条目只存具体事实，不给每条记录附一套处置办法。

~~~text
读到一段历史经验时，联系用户原始目标、你眼下要回答的问题或要作用的对象。
这段经验使哪个原先可能忽略的区别值得考虑？这个区别会改变本步的答案吗？
若会，看当前观察实际针对哪个对象、环境或版本，它支持、反驳，还是尚不足以判断？
已有证据足够就完成任务。证据不足且影响交付时，核查具体缺口，或明确当前能断言的范围。
~~~

例：同一条“各环境独立配置”在问测试值时，允许直接使用已有测试读数；把值写进生产方案时，测试读数只能支持测试环境。两个任务收到相同经验，应当允许两种不同表现。这是 F 的首个成对验收用例。

## 5. 交付物成型后的挑战试验

**启用条件**。先在目标宿主验证能否取得“草稿已成型、仍可修改、尚未对用户交接或执行”的真实事件和版本。GLM 提到的 `ops_asset_gate` 是待核对的宿主入口；确认它实际能看见的字段、时刻和覆盖路径。普通 Write 仅证明一个版本被写入。正文已经显示给用户后才到达的事件，只能做事后回放。无法证明交接前可见时，先交付离线回放，并把该路径记作未覆盖。

**触发与去重**。在可见的交付物中找到可引用的具体断言或作用目标，且存在对应的 cue 命中或本任务已经召回的相关经验，才对这项断言发起对照。去重以本任务、经验版本、实质断言和相关证据为依据。格式变化或重复事件不反复挑战；目标、结论或支持证据实质变化时允许再评估。此次复用已有事实不重置前置 lookup 收据。通用 MCP 保留宿主无此事件的运行方式。避免新增全局确认回合、强制落文件、Stop 整理或常态采集回复全文。

**给宿主的挑战模板**：

~~~text
待交接断言或作用目标：〈取自当前交付物的准确片段〉
相关历史事实：〈已召回的事实原文，含必要限定〉
本次依据：〈实际工具观察、用户原文或项目依据及其对象；无可定位依据时标为未取得〉

假设这项结论是错的，现有依据是否仍可能全部成立？
结合用户要求，保留、收窄或修正这份交付物。需要补查时，取能区分这两种情况的证据。
~~~

样例：“只有一行处于禁止态”即便为真，也可以与“用户指定的是另一行”同时成立。此时缺少的是需求与记录的映射。只有该映射有依据，才能决定具体哪一行正确。对于“master 实测”，则可直接读取目标引用并核对对象。模板不预告草稿有错，不把历史反例当作现场反证；正确草稿应当经得住挑战。

## 6. 观测与盲测

运行侧优先复用现有收据与诊断。最少区分候选命中、lookup 已生成、实际送达、重复抑制、可观察的交接前事件、挑战实际展示。只保留归因所需的版本、匿名样本或事件标识、状态和计数。正文、SQL 和业务资料只在有授权的隔离验收样本中使用。线上不可见的交付路径只能报告覆盖能力；有受控样本分母时才能报告覆盖率。

固定模型和提示词版本、工具、现场证据。以独立会话重放同一任务，各条件重复运行，评分者按预先标注的目标、允许动作和证据边界核对产物。对照组逐步增加一个变量：

| 组 | 条件 | 能回答的问题 |
| --- | --- | --- |
| A | 无经验 | 当前宿主的自然基线是多少？ |
| B | 现行正文、现行前置召回 | 已有召回带来了什么？ |
| C | 同一 cue 与时刻，换精简正文 | 写入和投递内容是否改善判断？此组隔离正文变量，沿用 B 的宿主提示。 |
| D | C 的正文，加新版前置 F 提示 | 新提示是否降低误用并保住原有收益？ |
| E | D 加交接前挑战 | 挑战的独立增益与误扰有多少？ |

样本必须含正确、错误和证据未定三类草稿，以及低风险擦边命中、同 cue 不同当前证据、不同入口关联同一经验、纯误读纠正后零新增、正文直出的未覆盖路径。额外加入“已查对记录但最终交付作用于另一行”和“经过数步后才把工作区读数写成分支结论”。隐藏答案；各组接收相同事实。传输层可使用合成模型，能力评估需用真实 GLM 宿主。涉及写库的交付物在隔离数据上回放。

| 指标 | 分母及解释 |
| --- | --- |
| 写入语义合格率 | 抽审记录中，来源支持断言、限定完整且确能改变具体判断的比例。宿主误读后从未调用写入，须在宿主回放里查。 |
| 召回准确性与送达率 | 标注样本上分别计算精确率、召回率；送达率单看应送达的版本。日志中的零命中不能自行证明零漏召。 |
| 错误或越界交付率 | 本应纠正或应限定的样本中，最终仍错误断言或作用于错误对象的比例。 |
| 正确草稿误改率 | 原本正确的草稿中，被挑战后改错的比例。 |
| 完成率与摩擦 | 分别统计有条件完成却提前收窄、无谓核查、额外工具调用或打断数。能取得证据的任务不能靠一律回答“无法确认”过关。 |

每组列出样本数、原始计数和成对结果；区分“只在新版正确”和“只在旧版正确”的案例。传输、幂等、跨项目隔离及数据完整性用确定性回归。对能力增益不预设成功百分比。交接前挑战默认试验性启用，评审 D/E 之间的纠错增益、误改和额外成本后，再决定扩大范围。小样本结果不支持扩大时，保留试验开关与基线。

## 7. 实现顺序与 GLM 交付物

参考源码为本地 memory-mcp 0.6.3，独立仓库为 vaxjaz/memory-mcp。开始改动前核对实际开发提交、发布基线、宿主适配器和当前数据库版本。文件名是定位线索，项目部署和发布规范以实际目标仓库为准。

| 顺序 | 主要入口（相对 memory-mcp 仓库） | 完成条件 |
| --- | --- | --- |
| 1. 固定基线与复盘样本 | `docs/DELIVERY_ACCEPTANCE.md`、现有协议及宿主验收脚本 | 保存现行协议、真实宿主能力、B 组行为和未覆盖路径，预先定义评分依据。 |
| 2. 写入与读取投影 | `internal/memory/experience.go`、`experience_cues.go`、`record_validation.go`、`agreement.go`，`internal/server/cue_schema.go` | 新写入形态、旧库读取、证据定位、幂等重试、实质修订、约定兼容、迁移和回退验证通过。 |
| 3. 召回与前置提示 | `internal/memory/recall_index.go`、`recall_lookup.go`、`experience_entrances.go`、`experience_delivery.go`，`internal/hooks/experience.go`，`internal/server/server.go`、`guide.md` | cue 别名、分页、索引重建、断线重试、仅送达一次、上下文重置均回归；实际 stdio 初始化、工具清单和调用通过；比较 B/C/D。 |
| 4. 宿主定向试验 | 经验证的宿主交接前入口与隔离回放 | 实际宿主展示准确引文、版本正确、重复事件去重。没有合适入口的宿主如实标注。完成 D/E 盲测。 |

预期交付：实现提交、协议与宿主提示、旧库兼容或迁移与回退结果、真实宿主的成对测试报告。报告把可复现的机制行为、观察到的 Agent 能力变化、尚未覆盖的路径分列。首版复用已有本地 MCP 和宿主模型，无需另接模型服务或向量库。实际宿主的交接前事件和有独立判据的业务验收样本，是验证新增能力的外部条件。
