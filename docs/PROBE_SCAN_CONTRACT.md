# 探针扫描契约（平台方案）

状态：第三版，与实现一致。4.1 到 4.8 全部已实现并通过验收。适用范围：R(x, M) 自动触发半边的 match 规则。本轮只面向 ZCode。

## 0. 这份方案解决什么

触发这一步做两件事：先决定一次工具事件里哪些文本交给 cue 的 match 表达式，再用表达式求值。求值器是通用的，本方案不改它。要定义的是前一件，它以前从来没有被定义过，行为是从代码里长出来的。

以前实测到的症状都来自这一个缺口：会话目录在子模块时 Read 兄弟模块的文件不扫描；Grep 的 `path` 等于当前目录时整次调用作废；一个字段不合格则全部字段丢弃；不扫描时没有原因；数组入参映射不了；内嵌手册里的示例永不匹配。

## 1. 已确定的决定

- **只有确认在项目内的路径才扫描。** 确认不了的不扫描，并把原因记下来。
- **不区分内置规则和自定义规则。** 所有工具规则都放在 `tool-probes.json` 一个文件里，新增和编辑都在这个文件里做。
- **Bash 默认只扫读文件和查找类命令。** 这是原有设计，有测试固定（`echo 入口词` 不能触发）。清单写在文件里，可以增删；想扫全部命令，就在项目规则里去掉 `scan`。
- **Write 和 Edit 默认列在文件里但停用。** 每个路由到 hook 的工具，每次调用都会多起一个进程，所以改文件的工具由项目自己打开。

## 2. 术语

- **事件**：客户端每次工具调用发给 hook 的数据，含工具名、入参、当前目录（cwd）。
- **规则**：文件里的一条记录，说明一个工具的哪些入参以什么名字交给 match 表达式。
- **字段**：交给 match 表达式的一个命名值。`tool`、`mcp_tool` 是工具名，`text` 是主要文本，`path` 是文件路径。
- **项目根**：`setup` 时绑定的项目目录。“项目”只指它。
- **入口词**：cue 里 `entrances` 的字面量。

## 3. 原则

- **P1 一个事件只有一个项目。** 就是项目根。作用域、路径归属、投递、结果事实全部用它。
- **P2 只有确认在项目内才扫描。** 确认不了的不扫描，并记录原因。
- **P3 一个字段的问题只影响它自己。**
- **P4 判定只有一份，每个结论都有原因。** `doctor --probe` 和真实 hook 调用同一个函数。
- **P5 问题挡在写入时。** 永远不会触发的 cue 不让进库。

## 4. 契约

### 4.1 一个配置文件

`tool-probes.json` 是工具规则的唯一来源。程序自带一份**默认规则**，用来在安装和升级时写进这个文件。

```json
{
  "tools": [
    {"tool": "Bash", "fields": {"text": ["command", "cmd", "script"]}, "scan": ["rg", "grep", "cat", "head", "tail", "find", "…"]},
    {"tool": "Grep", "fields": {"text": ["pattern", "query", "regex", "search_pattern"], "path": ["path", "file_path", "filePath"]}},
    {"tool": "Read", "fields": {"path": ["file_path", "path", "filePath"]}},
    {"tool": "Write", "enabled": false, "fields": {"text": "content", "path": "file_path"}},
    {"tool": "Edit", "enabled": false, "fields": {"text": "new_string", "path": "file_path"}}
  ],
  "projects": {
    "project:your-org/your-repo": [
      {"tool": "Write", "fields": {"text": "content", "path": "file_path"}}
    ]
  }
}
```

规则的各项：

| 项 | 含义 |
| --- | --- |
| `tool` 或 `mcp_tool` | 二选一。原生工具写准确名字；MCP 工具写不带服务器的裸名 |
| `enabled` | 省略或 `true` 生效，`false` 停用 |
| `fields` | 左边是交给 cue 的字段名，右边是入参里的路径。路径可以写一个，也可以写一组候选，取第一个存在的 |
| `scan` | 只对命令类规则有意义：列出命令名，命令文本里出现其中任一个（作为完整的词）才扫描 |
| `discover` | `"query"`：数据库类工具按已知的参数名找出查询语句。它自己决定字段，不能再写 `fields` 和 `scan` |
| `observe` | 登记上一个工具的结果。它按项目查找，所以只能写在 `projects` 下 |

- `tools` 对所有项目生效。`projects` 下的规则覆盖 `tools` 里的同名工具，一个工具在一个项目里只有一个来源。
- 路径最多 8 段，一条规则最多 8 个字段，全文件最多 128 条规则。

程序对这个文件的写入规则：

- **首次安装**：`setup` 发现文件不存在，就带着默认规则创建它。
- **升级**：`setup` 只把 `tools` 里还没有的默认工具补进去，不改已有条目。写之前在旁边留一份备份，并在输出里列出补了什么。`--dry-run` 只报告，不写。
- **想停用某个工具**：把它的 `enabled` 改成 `false`。直接删掉的默认工具会在下次 `setup` 时重新列出。
- **文件里没有 `tools` 一节**（旧格式的文件，或者文件还不存在）：默认规则照常生效，doctor 给出 `probe_tools_implicit` 或 `probe_config_missing`，并提示重跑 `setup` 把它们写进文件。显式写 `"tools": []` 则不扫任何默认工具。
- **doctor 列出生效的规则**：`probe_surface` 给出每个项目的每个工具来自哪里（`project`、`tools` 还是 `default`）、映射了哪些字段。

回退到旧版本时，旧程序读不懂带 `tools` 的文件，需要连同备份的 `tool-probes.json` 一起恢复。

### 4.2 两级判定

所有工具走同一套判定，没有例外。结果写在 `doctor --probe` 的 `tool_input.outcome` 和每个字段的 `status` 里。

**整个事件不扫描：**

| `outcome` | 含义 |
| --- | --- |
| `tool_disabled` | 规则里写了 `"enabled": false` |
| `operation_not_scanned` | 规则有 `scan`，命令文本里没有列出过的命令名 |
| `instruction_file` | 命令读的是指令或技能文件 |
| `no_eligible_text` | 没有任何字段留下来 |

**单个字段不参与，只影响它自己：**

| 字段 `status` | 含义 |
| --- | --- |
| `missing`、`empty`、`unsupported_type` | 不存在、为空、不是单个字符串也不是单个数字或布尔值 |
| `field_too_large` | 这一个值超过 32KB |
| `text_budget_exceeded` | 加上它，事件的文本总量超过 64KB |
| `element_limit` | 数组超过 64 个元素，多出的不取 |
| `instruction_file` | 这个路径是指令或技能文件 |
| `path_outside_project`、`path_unresolved` | 路径不在项目内，或无法确认 |

**指令和技能文件**按路径的每一段判断，所以相对路径和绝对路径结论相同：文件名是 `agents.md`、`claude.md`、`gemini.md`、`skill.md`，或者经过 `.agents`、`.claude`、`.codex`、`.cursor`、`.qoder` 目录。

### 4.3 路径归属

- **判定对象**：名字叫 `path` 的字段。同样的文本换一个字段名就是普通内容。
- **基准**：项目根，不再用会话目录。
- **步骤**：
  1. 以 `~`、`$变量`、`%变量%` 开头或包含它们的路径，真实位置未知，记 `path_unresolved`。
  2. 相对路径以会话目录补全，再与项目根做一次字面比较，已经在外面的记 `path_outside_project`。
  3. 从项目根开始逐段走：遇到符号链接或 junction，读出它指向的位置，那个位置必须也在项目内；走到尚不存在的那一段就停，因为后面不可能再有链接。
- **结论只有两种**：

| 结论 | 处理 |
| --- | --- |
| 确认在项目内（含正好等于项目根，含经链接指向项目内） | 参与 |
| 不在项目内，或无法确认 | 不参与，并给出原因 |

- **它只管路径字符串本身。** 路径不参与，不影响同一事件里 `text` 的扫描。

### 4.4 字段名

每个事件固定带两个工具名字段：

- `tool`：客户端发来的原样工具名。MCP 工具是全名 `mcp__服务器__名字`。
- `mcp_tool`：MCP 工具的裸名，非 MCP 工具为空字符串。

文件里注册 MCP 工具用的是裸名，cue 里却只能写带服务器名的全名，而不同客户端可能把 `-` 归一成 `_`。两套叫法对不上，`when tool eq "login"` 这类写法就必然失效。有了 `mcp_tool`，条件写成 `{"field": "mcp_tool", "op": "eq", "value": "login"}`。

### 4.5 每次判定都留痕

- 每个字段给出名字、入参路径、状态；事件给出结论。
- `doctor --probe` 输出同一份结果。它不再用当前终端目录兜底 cwd，事件和 `--project` 都没给时直接报错。
- 事件到了 hook 但没被扫描时，记一行 `probe_skipped`，内容是工具名、生效规则的来源和原因，不含任何入参内容。用 `doctor --session` 查看。
- **事件日志有上限**：保留最近 2 万行，更早的自动丢弃。`doctor` 只读每个会话最近的 20 条。

### 4.6 写入时拦截永远不会触发的 cue

一条 cue 如果引用了没有规则能提供的工具、字段或结果，它的条件就永远不可能满足，存进去也永远不会触发。`memory_experience_record` 和 `memory_reference_record` 在写入和修订时检查这一点。

- **一条表达式能触发**，当且仅当这个项目有一条生效的规则同时满足：表达式里对工具的限定（`tool`、`mcp_tool` 等于某个名字），并暴露表达式引用的全部字段。
- **只在能确定时拒绝。** 条件出现在 `any`、`not` 之下，或对工具名用了 `eq` 以外的比较时，无法判断，一律接受。
- **报错指出位置和出路。** 例如 `experience.cues[0].matches[0].when: no rule in tool-probes.json registers a tool named "login"; "login" is registered as an MCP tool, so name it with {"field":"mcp_tool","op":"eq","value":"login"}`。工具列在文件里但停用时，提示把 `enabled` 改成 `true` 并重跑 `setup`。
- **配置文件读不了时不拒绝**，交给其它校验。
- **doctor 列出库里已有的这类 cue**（`unreachable_cues`），升级时据此审计，已有记录不会被改动。

在本机真实库上核对的结果：现有 24 条规则零误判。

### 4.7 文档示例即测试

手册里的示例以前没人验证过：login 示例的条件写成了 `when tool eq "login"`，而 `login` 是按裸名注册的 MCP 工具，这条规则永远不会匹配。现在内嵌指南的每个示例都是测试。

- **`internal/hooks/guide_examples_test.go` 解析指南里的每个 JSON 代码块。** 规则块按“后面的覆盖前面的同名工具”合并成一份配置，必须能加载。
- **cue 示例必须能存、能触发。** 每个 cue 示例先过 4.6 的可达性检查，再写进隔离库。
- **印刷出来的事件样本必须命中它声称的规则。** 结算示例的样本命中 `settlement_code` 和 `settlement_code_write_gate`，login 示例的样本命中 `credential_self_fetch`，数组示例的样本命中 `ask_example`；手册里列出的近似但不该触发的情况，一个都不命中。
- **接口文档与程序逐项核对。** `scripts/check_scenarios.py` 读出程序自己的接口定义和命令行帮助，`docs/API.md` 里的每个参数、每个必填标记、每个命令行参数都必须与之一致。
- **示例一改，测试就失败**，所以手册不会再悄悄过期。

### 4.8 数组入参

- **路径仍然用点分段。** 每一段是三种之一：对象键、数组下标（如 `0`）、`*`（数组的每一个元素）。
- **路径终点的值必须是字符串。** 终点是字符串数组时每个元素都算，不需要额外写法。
- `[]` 和 `[*]` 不支持，报错时给出允许的写法和例子。

| 入参形态 | 写法 | 取到的文本 |
| --- | --- | --- |
| `"tags": ["a", "b"]` | `"text": "tags"` | `a`、`b` |
| `"questions": [{"question": "…"}, …]` | `"text": "questions.*.question"` | 每个元素的 `question` |
| 同上，只要第一个 | `"text": "questions.0.question"` | 第一个元素的 `question` |

- **每个元素是一段独立的文本。** 入口词按单段确认，不会把两个元素拼在一起凑出一个入口词。
- **条件里写明字段名时，比较这个名字下的每一个值。** 例如 `{"field":"text","op":"contains","value":"对账"}`：`text` 映射到数组时，任何一个元素含“对账”即成立。以前只比较第一个值，后面的元素命中不了。
- **上限。** 一个字段最多取 64 个元素，每个值不超过 32KB，并计入事件的 64KB。
- **观察结果显示数组的内层结构**，路径与配置写法一致，例如 `questions.*.question`、`questions.*.options.*.label`，照着填即可。
- **已有的路径全部不变**，旧文件不需要改。

## 5. 升级后的行为变化

**会比以前多触发：**

1. 会话目录在子模块时，读项目内其它模块的绝对路径。
2. Grep 的 `path` 等于当前目录或项目根。
3. 某个字段不参与时，同一事件里的其它字段照常扫描。
4. 默认的命令清单多了 `head`、`tail`、`find`、`awk`、`ls` 等读文件和查找类命令。

**会比以前少触发：**

5. 项目规则的 `path` 字段不在项目内时，路径字符串本身不再参与匹配。同事件的 `text` 不受影响。
6. 相对路径补全后落在项目外的，路径字符串不再参与匹配。
7. 没展开的 `~` 和环境变量路径不再被当作项目内。
8. 写到指令或技能文件（如 `AGENTS.md`）的操作不再扫描，所有规则一致。

**新增能力：**

9. 数组入参可以映射，见 4.8。
10. cue 里可以用 `mcp_tool` 写 MCP 工具的条件。

**文件变化：**

11. `setup` 给 `tool-probes.json` 创建或补上 `tools` 一节，不改已有条目。

## 6. 保留不变的行为

- 未绑定的目录不扫描，没有全局兜底。
- 唤醒策略关闭则不扫描。
- Bash 默认只扫清单里的命令；Write、Edit 默认停用。
- 一个工具在一个项目里只有一个来源。
- 经链接或 junction 指向项目外的路径不扫描。
- 正文已交付后同一关联静默，每个输入只打断一次。

## 7. 验收

- `internal/hooks/probe_rules_test.go` 和 `probe_config_test.go`：规则模型、文件的创建与补齐、字段独立判定、路径归属（含链接指向项目内、项目外、循环）、数组、命令清单、留痕。
- `scripts/check_tool_matrix.py`：通过真实程序的 76 项矩阵，覆盖载体、会话目录、路径写法、入参形态和文件迁移。
- `scripts/check_capability_matrix.py`：能力矩阵的总览与逐格计数一致。
- `scripts/check_scenarios.py` 的 147 项里有对真实报错文字的检查：缺必填项、项目未绑定、范围不符、文件不存在。
- `scripts/acceptance.py`：一条命令跑完全部门禁。

## 8. 未验证的事项与风险

- **其它宿主的事件没测过。** Codex、Qoder 发来的工具名和入参键名是否都在默认规则里，没有跑过原生会话，留到下一轮。
- **WSL 路径里 Linux 一侧的符号链接看不到。** 经 `\\wsl$\` 访问时，系统不一定把它报告为链接。
- **ZCode 原生会话验证到哪一步。** 本机真实客户端升级后，当前会话的工具调用和新开会话的启动都由新程序处理 hook，调用正常完成。在已绑定的项目里走完“读文件→拦截→查询→送达”的一轮还没有做：判定已用 `doctor --probe` 对真实库只读验证，完整一轮留给使用者在试用项目里验证。
- **打断会增加**，见第 5 节前四条。
