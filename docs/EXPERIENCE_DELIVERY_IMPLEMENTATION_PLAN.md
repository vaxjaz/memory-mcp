## 1. 已确定的边界

### 1.1 必须保持的行为

1. 经验是核心对象；类、方法、路径、配置和业务动作是识别入口。业务经验可以没有代码锚点。
2. 宿主 Agent 理解主需求、当前步骤和具体疑问，并构造 lookup 的任务与查询。hook 不根据一条 grep 猜完整需求；MCP 不调用另一个模型解释任务。
3. 有明确索引命中，才进入自动介入逻辑；无命中静默。入口之间可映射到同一经验、同一关联点。
4. 历史内容保留条件、被反例挑战的推断、观察结果、必要边界和证据位置。不得把它改写成当前任务的结论或指定修改位置。
5. 未交付经验的稳定查询触发仍保留。正文通过 lookup 返回一次，不再由 hook 复制一份。
6. 后续增量提示取决于新的可观察关联点，不取决于次数、时间、工具名变化或文件访问数量。
7. 投递记录由系统维护。不得要求 Agent 登记已读、已理解、已处理、不适用、skip 或 complete。
8. 投递记录只能说明系统返回过什么。它不能说明当前适用、调查完成、模型理解、操作获授权或代码安全。
9. Agent 自主调用 lookup/read 始终正常返回材料。自动提醒去重不能禁止、限流或代替主动检索。
10. 保持无原文采集、无每轮通用提醒、无异步经验写入、无 Stop 整理。不要为此引入任务申报流程、第二个模型或向量服务。
11. Agent 根据当前证据判断经验不适用、风险已经消除、当前实现没有问题，均为允许且有价值的结果。系统不得据此要求继续调查、修改代码、采纳历史做法或登记拒绝理由。首次强触发约束的是材料查询与交付，不是后续结论。

### 1.2 不追求的保证

系统不模拟“第 N 次想到后开始怀疑”，也不判断 Agent 脑中是否仍记得经验。没有新关联时允许静默，Agent 仍可根据当前证据重新质疑。

该方案控制增量交付量；它不提供可覆盖的模型记忆槽，不会删除已经进入对话的旧正文。相关经验越多，上下文仍会增长。自动介入也不能覆盖没有任何可观察工具入口的纯思考过程。

本文将用户已认可的行为契约和建议的工程默认值分开：是否调查由 Agent 决定、按关联点增量投递等属于不可退回的契约；字节预算、字段命名和表布局是建议实现值，可以经测量调整，但不能借调整改变行为契约。

## 3. 核心数据模型

下面是逻辑模型；可复用已有表。字段名可兼容调整，行为契约不能省略。

### 3.1 Experience 与 Cue

`experience_root_id` 是经验稳定身份；`revision_id` 标识该条经验的内容版本。继续保留紧凑反例正文。

每条经验新增 `cues`。一个 cue 表示这条反例与当前工作的一个有依据的关联点，不等于一个类、一个文件或一个搜索词。

```json
{
  "experience_root_id": "E1",
  "revision_id": "R2",
  "cues": [
    {
      "cue_id": "remark_change",
      "label": "业务备注变化",
      "text": "历史回馈中，业务备注已更新，新增回馈日志仍保留旧文本。",
      "evidence_refs": ["evidence-1"],
      "entrances": [
        {"kind": "code_symbol", "value": "WorkOrder.remark"},
        {"kind": "business_signal", "value": "调整回馈备注"}
      ]
    },
    {
      "cue_id": "log_input",
      "label": "日志生成取值",
      "text": "历史回馈日志曾从独立回馈参数取文本，业务备注变化未传入。",
      "evidence_refs": ["evidence-2"],
      "entrances": [
        {"kind": "code_symbol", "value": "FeedbackLogBuilder.build"}
      ]
    }
  ]
}
```

以上业务事实、类名和证据标识都是说明协议的假设性 fixture，不是项目真实经验，不得写入真实经验库。

cue 的约束：

- `cue_id` 在同一经验内稳定；不能由工具调用 ID、文件哈希、当前时间或随机数生成。
- 多个入口可以指向同一个 cue。增加入口别名不产生新 cue，不重置已提示记录。
- 新 cue 必须有不同的风险关联事实或条件，并引用真实证据。不能把类依赖图每个节点自动转成 cue。
- 短文本由记录经验的 Agent 在证据核实后同步写入。hook 直接读取，不临时调用模型总结，不截取正文开头，不用标题代替反例。
- 一个 cue 不是一个待完成任务，没有 `needs_investigation`、`verified`、`done` 等认知状态。
- 条件、观察、因果解释要区分。未核实的原因不能写成已证实的解释；不允许用“应该修改 X”代替历史事实。
- 新经验允许纯业务入口与业务证据，不能再强制至少有一个代码类或现存源码路径。
- 若两个 cue 只是在不同类名上复述同一个关联，合并为一个 cue；若事实确实独立到不属于同一反例，拆成不同经验。

只对经验事实、适用条件、边界或有实质意义的 cue 内容修订生成新内容版本。入口别名、索引重建、定位行号移动、工具名称适配不能借机刷新所有投递记录。不要用当前代码文件哈希冒充经验内容版本。

### 3.2 接收方与投递记录

```text
consumer = host + scope + project_binding + session_id + agent_id + context_epoch

body_delivery 唯一键 = consumer + experience_root_id + revision_id
cue_delivery  唯一键 = consumer + experience_root_id + revision_id + cue_id
```

`context_epoch` 只用于宿主明确报告的上下文生命周期变化，不是用户轮次，不是任务编号，不是时间窗口。

建议最小记录：

| 记录 | 必要信息 | 含义 |
| --- | --- | --- |
| challenge | ID、接收方、候选经验版本、触发 cue、关联原生事件 | 有哪些尚未交付的材料触发了本次查询要求 |
| response receipt | 不透明 receipt ID、实际结果条目与版本、challenge 关联、生成/宿主观察状态 | 识别一份具体工具结果，避免依赖 Agent 声明 |
| body delivery | 接收方、经验版本、receipt ID | 宿主成功工具结果事件已经观察到该正文 |
| cue delivery | 接收方、经验版本、cue ID、来源事件/receipt | 这个关联已在首次召回或增量提醒中交付/发出 |

可以保存故障诊断时间，但不得用时间或查询次数决定何时重新调查、何时重新提醒。原始用户输入、回答、命令全文、业务工具原文不能作为新增长期投递日志。

### 3.3 经验纠偏与沉淀：时机保留，写入结构扩展

继续采用现有准入原则：用户纠偏或 Agent 自主发现触发核实；发现有价值的反例、风险条件或遗漏边界后，依据当前代码、运行或业务证据同步保存紧凑经验。用户纠正是一条核实信号，不能未经核实直接当成历史事实；正常任务完成、进度、普通事实与“这次没有问题”不自动成为新经验。

需要的改动集中在 `memory_experience_record` 的结构和一致性：

- 保存正文时，同时提交经核实的 cue 短文本、证据引用和入口映射。由当时理解事实的 Agent 编写，MCP 负责机械校验和事务保存；不能临时在 hook 中总结。
- 正文、cue、入口索引和版本在一次事务中更新，避免正文已修订但 hook 仍发旧短线索。不要新增独立的“补齐 cue”强制交互流程。
- 更新记录工具 schema 与简短工具说明，让 Agent 在原有同步写入调用中提供这些字段。不要通过每轮提醒、Stop 整理或另一个模型补齐。
- 新增有证据的入口别名，指向既有 cue；不因补充入口就创造新经验、改变正文版本或重置投递记录。
- 实质纠正既有事实/条件/边界时，通过既有 `previous_id` 修订同一经验并保留历史；独立的新反例才新增经验。正常重复写入保持幂等。

| 当前发现 | 沉淀处理 |
| --- | --- |
| E1 的已知适用条件在本次不成立 | 不需要写回，也不记录“本次拒绝 E1” |
| 当前实现已修复历史风险，历史记录本身仍真实 | 不因一次不适用否定历史；没有可复用新增信息时不写回 |
| 核实发现 E1 遗漏了有复用价值的例外或版本边界 | 修订 E1 的条件/边界，并同步对应 cue |
| 当前证据足以证明原记录的某个断言有误 | 修订原记录，保留证据与历史；不能仅凭现版本不同断言旧事件没有发生 |
| 发现新的独立故障机制，且有事实证据 | 新建经验，并提供对应的紧凑事实与真实入口 |

投递账本与经验库分开：发送过 cue、查询过正文、Agent 没有采纳，都是流程事实，不得自动提升为长期经验或作为修改经验真伪的依据。

## 4. 首次触发与 lookup 成功回执

### 4.1 首次触发

1. 宿主工具事件经过窄 matcher；提取允许字段中的识别线索。
2. 本地索引返回全部实际匹配的经验版本、cue ID 与入口证据；合并同一经验、同一 cue。
3. 对尚无正文投递记录的经验创建/复用 challenge。阻止本次工具请求，返回简短查询要求与真实 challenge ID。
4. Agent 根据主需求和当前步骤构造 `task`、`questions`、`queries`，调用 lookup。
5. MCP 执行现有检索，把 challenge 候选与自主查询结果共同呈现。索引明确命中的候选不能因 Agent 查询措辞不同而被悄悄过滤。
6. lookup 返回紧凑正文，宿主正常接收工具结果。这里就是正文进入上下文的通道。

block 理由只需要表达“当前操作命中经验入口，结合完整任务与当前疑问 lookup，并使用 C1”。不要附正文、长规范、标准调查步骤或固定解决路线。

hook 自己可以查本地索引，但不能替 Agent 构造语义问题并悄悄完成 lookup。Agent 仍然拥有下一步决策权；被阻止的工具不会由 MCP 自动重新执行。

### 4.2 响应生成不等于成功交付

在 MCP 构造响应时，仅记录 `response_generated`，附一个不透明 `receipt_id`。receipt 绑定实际输出的 ID、版本和分页，不复制整段正文。

对本记忆服务的 lookup 注册窄范围 PostToolUse 处理：

1. 根据宿主事件确定真实接收方、调用 ID、工具名、错误状态。
2. 从该工具结果的既定结构提取 receipt ID，核对服务、项目、challenge、版本与实际条目。不要正则扫描任意业务文本寻找 receipt。
3. 只在结果确实成功、完整条目存在且归属相符时，写入 body delivery。
4. 对本次 challenge 中、且对应正文已交付的触发 cue 写入 cue delivery。
5. 返回空上下文。回执处理不能再把正文、短引用或“查询完成”提示注入一次。

`PostToolUse` 事件名称本身不一定保证成功，必须按具体宿主检查 MCP `isError`、传输错误及解析结果。生成响应后崩溃、传输失败、分页没有返回某条记录，都不得把该条记为已投递。

宿主成功结果事件证明工具结果已到达该宿主执行路径，仍不证明下一次模型请求实际包含全部材料，更不证明理解。状态名称、日志、报告必须保持这个边界。

主动 lookup 没有 challenge 时也可登记实际返回的正文，但必须从真实宿主事件获得 consumer。不能让 Agent 自报 session/Agent ID。该查询没有触发的 cue 不凭空标为已提示。第一阶段不增加 memory_read 的强制回执或拦截流程；read 保持自由读取。

### 4.3 为什么原操作重试会静默

重试时重新匹配，若命中 `E1/R2/cue-A`，且正文和 cue-A 已有记录，hook 返回空输出。

不比较两条命令是否语义相同，也不要求复用 tool call ID。新的调用 ID、grep 改写、bash 改 read，只要落在同一 cue，都走相同规则。tool call ID 只用于原生事件关联和故障排查。

E1 的记录不能释放 E2。不存在“本轮查过一次，因此其余所有经验都放行”的全局通行证。

### 4.4 最小接口改动与事件关联

lookup 保留现有 `scope/project/task/questions/queries/challenge_id/cursor` 语义。新增 cues 属于经验记录接口，不能要求 Agent 在每次 lookup 时自行计算 cue ID 或投递状态。示意查询如下，业务信息仅为 fixture：

```json
{
  "scope": "project:example",
  "task": "维修工单 WXN002 的需求要求调整回馈日志备注；当前正在定位回馈相关代码。",
  "questions": "当前实现中，业务备注修改与新增回馈日志文本之间是什么关系，是否有历史反例？",
  "queries": [
    {"terms": ["回馈", "日志备注"], "match": "all"},
    {"terms": ["WorkOrder"], "match": "any"}
  ],
  "challenge_id": "系统实际签发的 C1"
}
```

成功返回在现有单份 JSON text 结果中增加 `receipt_id`。继续返回明确的经验身份、内容版本与完整紧凑正文，并保留 `has_more/next_cursor`。内部 receipt 必须列出该页真正序列化成功的条目；不能记录整个候选集合。已有 `root_id` 可作经验身份，`id` 可作记录版本，不必额外返回多套同义 ID。

生成响应时的 `challenge_outcome` 只能描述 `response_generated` 或仍有未返回候选等服务端事实；此时不能返回“宿主已收到”。PostToolUse 写入系统成功回执后，后续 hook 从数据库读取放行依据，不再额外调用一个“完成工具”。

为避免上下文切换时串账，适配器必须在 lookup 发出时绑定原生 `tool_use_id` 与当时的 consumer/context_epoch，再用同一次调用的 PostToolUse 完成关联。可用针对本服务 lookup 的窄 PreToolUse 观察器；该观察器只记录调用标识与必要绑定，始终放行，不做经验匹配、不保存任务原文、不增加提示。不能把普通 lookup 的晚到结果直接登记到 PostToolUse 发生时的新上下文。

如果某宿主没有可靠调用 ID，必须使用该宿主已验证的等价关联方式；不能靠 task 文本哈希、时间邻近或“最后一条查询”拼接并发请求。

原生 hook 回执处理内部完成；不新增 Agent 必须调用的 `memory_ack`、`memory_complete` 或“是否调查”API。记录 API、lookup 返回、原生事件与数据库逻辑分别做兼容测试，安装时同步更新 MCP schema 与宿主配置。

## 5. 短引用的确定发送算法

### 5.1 正常决策表

| 当前事实 | hook 行为 | 新增上下文 |
| --- | --- | --- |
| 无明确匹配 | 正常继续 | 无 |
| E1 当前版本正文尚未交付 | 创建/复用 E1 的查询 challenge | 简短查询要求 |
| 正文已交付，命中 cue-A 已提示 | 正常继续 | 无 |
| 正文已交付，命中 cue-B 尚未提示 | 正常继续，发送 B 的短引用 | 一条具体历史线索 |
| 同一次调用多个入口都映射到 B | 合并后处理 | 最多一份 B |
| 同一次调用命中多个新 cue | 按经验合并，保留不同事实 | 有限的增量线索，不重复经验前缀 |
| Agent 主动 lookup/read | 正常执行，不应用自动提示抑制 | 正常查询结果 |

```text
matches = match_observable_entrances(event)
matches = distinct(matches, experience_revision, cue_id)

unseen_bodies = matches whose body_delivery is absent
if unseen_bodies is not empty:
    return short_block_reason(create_or_reuse_challenge(unseen_bodies))

new_cues = matches whose cue_delivery is absent
if new_cues is empty:
    return empty_output

emitted = atomically_claim_and_render(new_cues, output_budget)
return nonblocking_additional_context(emitted)
```

混合事件中既有未交付的 E2，又有已交付 E1 的新 cue 时，优先完成 E2 查询，不在 block 理由中再拼一批 E1 短引用。未发送的 E1 cue 不能标为已提示；后续再次实际命中时仍可发送。不得定时补发或主动另起一轮。

### 5.2 首次正文究竟覆盖哪些 cue

首次 lookup 的正文可能包含经验的全部事实，但 cue delivery 表示“哪个当前关联已经被提示”，不是“正文里包含哪些词”。

首次由 A 触发，只将 A 标为已提示；不能把 E1 所有 cue 一次性全部消耗。之后首次进入 B，仍可附 B 的短引用。如果同一个 challenge 实际由 A、B 共同触发，两者都随这次正文交付登记。

### 5.3 短引用格式与预算

正常格式：

```text
E1@R2 · 日志生成取值：历史回馈日志曾从独立参数取文本，业务备注变化未传入。
```

短文本目标为一句话、约 40～80 个汉字。建议第一版字段硬上限为 160 个 Unicode 字符；这是材料长度保护，不是 Agent 调查规则。条件放不下时重写记录或拆分真正独立的经验，禁止静默截断、删掉否定或例外。

短引用只含 ID/版本、关联标签、具体历史线索。不要携带全部索引词、所有关联类、整份证据对象、定位哈希、通用规程及“必须验证”指令。

这里的“短引用”是直接加入 Agent 正在自主推进的当前任务上下文的短经验材料，必须包含可辨识的具体反例事实。只有界面通知、hook 日志、裸 ID，或“注意某问题，必要时查经验”的通用提醒，都不算符合要求。时机是 Agent 自主工具操作触发后的正常继续执行点，不为提醒单独启动整理任务。

短引用只能唤起该版本正文已经交付过的风险事实，并建立当前入口与该事实的联系。如果新增 cue 实际包含此前正文没有的新风险，必须形成经验的实质修订或独立经验，按未知正文走首次强触发；不能把首次风险披露降级成轻提示。

为单次自动 additionalContext 设明确预算，建议默认 1024 UTF-8 字节；实现者应以真实宿主测量校准并报告。批量超限时：

- 只把实际输出的 cue 标为已发出，其余保留未发出状态。
- 在预算内保留简短的“另有未展示关联”标记，必要时提供沿用现有检索机制的可读取分页引用；不能宣称列表完整。
- 未发出的 cue 只在后续再次相关命中，或 Agent 主动读取时继续交付；不得为了清空队列反复制造新轮次。
- 这里的剩余项对应正文已经交付的经验。首次未知经验的候选不能套用这个规则静默丢弃，必须在 lookup 分页中明确保留。

单条完整 cue 若超过总输出预算，应在写入/配置校验时发现冲突，不得运行时把事实截成残句。实现时需要同时测试字节预算与中文字符边界。

## 6. 并发、分页和故障

### 6.1 并发幂等

body delivery 与 cue delivery 使用唯一键及事务。多个并行工具首次命中同一个 B，只允许正常路径中一个发送者取得该 cue 的发送权。

相同接收方、相同候选版本集合的未完成 challenge 可以复用。不同经验的 pending 不能被一个 completed 标记整体覆盖。候选快照、实际返回条目与分页收据必须可对应，不能在查询过程中无声修改候选集合。

数据库提交与宿主接收 stdout 不构成原子事务。发送前预留、输出失败撤回、进程崩溃恢复应有测试；可以复用现有 journal/receipt，避免搭建业务工作流。必须区分“准备发送”“hook 已输出”“宿主观察到工具结果”，不能把数据库 insert 宣称为端到端 exactly-once。

故障恢复可选择保守重发，并明确极端窗口可能重复；不能为了绝不重复而把未发出的内容永久吞掉。正常并发与事件重放应幂等，不得依靠“过几分钟再提醒”修复。

### 6.2 分页和候选保全

只确认实际成功返回的完整条目。分页 1 返回 E1、分页 2 尚未返回 E2 时，E2 不能标为已交付。正文只存在 ID、截断摘要或错误对象时也不能登记完整正文交付。

明确索引候选要进入 lookup 结果集合，即使 Agent 的关键词没有再次命中它。结果可以标注其来源为入口候选，适用性仍由 Agent 判断。候选已撤销、失效或换版本时应返回明确状态并更新 challenge，不能无限要求读取已经不存在的版本。

旧 TTL 不能作为正常重新提醒策略。允许宿主进程 deadline、锁恢复或过期请求的故障处理；它们只处理技术有效性，不能生成“现在需要重新调查”的判定。

### 6.3 故障与不支持的宿主

数据库故障、无法解析回执、宿主不提供必要事件、lookup 返回失败，不可伪造完成。通过已有诊断渠道说明降级，操作故障按有界 fail-open 处理，不能形成无限 block。

区分“技术故障下不阻塞工作”与“材料已交付”。降级不写 body/cue 成功记录，不以每轮提醒补偿，不恢复 V1 全量注入。

若某宿主不能可靠观察 lookup 的工具结果，不得声称该宿主支持完整交付机制。先完成真实宿主协议验证；可以提供明确关闭的介入能力和正常主动检索，但不能偷偷把 generated receipt 当成功回执上线。

## 7. 会话与上下文生命周期

| 事件 | 处理 |
| --- | --- |
| 用户说“继续”、发新消息、原生 turn_id 变化 | 不清空正文或 cue 投递记录 |
| 工具进程、MCP 进程正常重启 | 持久化记录继续使用；不能重新广播 |
| 同一 Agent、同一上下文恢复 | 保留记录，重复 SessionStart 幂等 |
| 新 Agent / fork | 隔离接收方，不把父 Agent 的交付当作子 Agent 已收到 |
| 宿主明确报告 clear/compact | 新上下文代次；下一次相关命中按未知正文处理，不立刻全库回灌 |
| 宿主不报告的上下文裁剪 | 承认不可检测，不通过读 transcript 或定时重置猜测 |
| 经验事实有实质修订 | 新版本独立交付，旧版本记录不能覆盖 |
| 只增加入口别名或重建索引 | 保留投递记录 |

compact 后保守重取会增加一次实际需求相关的交付；不能因为摘要“可能保留”就永久只给 ID，也不能把所有曾见经验在 compact 后一次灌回。具体事件来源和去重方式由适配器验证。

同一会话换需求并不自动清账；系统不能仅根据新一句用户消息推断“全新任务”。本方案不保证每个新需求都会重新播报所有旧 cue。需要按任务对象重新提醒属于后续独立需求，不能在本次暗中引入任务申报或猜测任务 ID。

“在 Agent 自主任务中追加上下文”描述交付位置，不表示每个任务、每个拆解步骤或每次思考都追加。只有真实工具入口命中未交付正文或尚未提示的 cue 才可能产生新的记忆内容；一个完整任务可以零追加。相同接收方/上下文内已投递的内容不因进入下一步骤重新复制，Agent 主动检索仍照常返回。

## 8. 多入口与业务观察

识别结果统一成 `(experience_root_id, revision_id, cue_id, matched_entrance)`，下游投递逻辑不关心它来自 bash、文件扫描还是业务工具。

入口注册需要真实证据支持关联；不递归展开整个类依赖图，不因父目录命中就把所有经验当相关，不把 class 名称当唯一入口类型。

OA/业务流程可以先读取单据才出现真实业务动作和对象标识。窄范围 PostToolUse 可从允许的结构化字段观察实际入口并绑定真实对象，供后续相关操作触发。只保留必要标识/匹配 ID/摘要哈希，不能保存原始单据、聊天或全部工具输出。

业务观察的短期对象绑定与正文投递状态是不同数据：对象观察失效不能把已交付的全部经验重置。仅有 OA 编号但尚不知道其内容时，不允许凭编号猜业务语义。

若识别线索只在最后一次业务工具结果中出现、后续没有适合的可拦截操作，现有“下一次 PreToolUse 强触发”可能没有机会执行。必须在覆盖说明中标明，不伪造“已经阻止了刚完成的工具”。本次不要补出 Stop 阶段或全局每轮扫描。

未知工具/包装器、没有稳定字段、纯文本无工具的场景需要明确覆盖边界。扩展入口应新增明确的适配和 fixture，不能改成拦截所有工具全文。

## 9. 模型可见内容与性能契约

存储模型与返回 DTO 分开：可保留内部索引、版本、定位和收据，正常模型可见正文只交付必要历史事实、条件、边界及紧凑证据位置。不能把内部数据库对象整体 JSON dump 出去。

正文目标是几句话，一条经验一个反例机制；尽量在约 150～300 个汉字内表达核心，证据定位另计。现有字段/JSON/单页硬预算作为上限保护，不能当鼓励填满的目标。超过目标时先审查是否混了多个经验，不能删除必要条件。

保留单份 MCP text 结果。不得把同一正文同时放在 text、structuredContent、hook additionalContext 和通用提示模板中。

性能分开测量：

- hook 进程启动、索引匹配、SQLite 访问与回执写入。
- MCP 查询时间与序列化字节数。
- block 引起的 Agent 额外生成/工具往返。
- Agent 是否重做调查，以及实际任务总耗时。

SQL 很快不能证明用户感觉很快。没有新增 cue 的重复搜索必须产生零新增记忆正文/提示 token，但 hook 本地执行本身仍可能有成本。

正常自动上下文量应随“首次交付的不同经验正文 + 首次出现的不同关联点”增长，不随同一关联点的工具调用次数增长。主动查询、真实版本变更、明确 compact 和故障保守重发应单独计量。

## 10. 实施顺序

1. 核实实际工作树与运行环境，保护已有改动；收敛重复函数和表名混用，建立可构建基线。不要用旧 HEAD 覆盖现有草稿。
2. 定义 cue、入口映射、consumer、正文投递、cue 投递与 response receipt；复用现有事务与迁移设施。
3. 扩展记录 API 的 cues 和纯业务入口；实现静态校验、稳定 ID、证据引用及内容/索引修订分离。
4. 分离模型可见 DTO，确保反例事实、条件与边界保留，去掉重复内部字段；保留现有单份 JSON 返回。
5. 接通 lookup receipt 与原生成功工具结果事件。先证明真实结果路径，再切换放行判断。
6. 将 PreToolUse 改成本文决策表；移除按输入轮次整体放行及时间冷却策略。
7. 实现 cue 合并、短引用、输出预算、并发领取与失败恢复。原操作重试不需要额外“识别重试”模块。
8. 保持多入口映射和业务观察，增加真实的非 bash / 无代码经验 fixture。
9. 完成状态迁移、配置 matcher、诊断与生命周期处理；更新 README、安装/试用文档和版本说明，删除与新契约冲突的旧指导。
10. 按下面的验收矩阵完成自动测试和真实宿主试用，再交付源码、构建与运行版本证据。

单独实现可单测的决策函数，输入匹配集合与投递事实，输出 `silent / challenge / cues`。持久化、宿主协议和内容渲染分别验证，避免把整个语义埋在 hook 字符串拼接中。

## 11. 迁移与兼容

迁移前确认真正的 data_dir，停止混用的新旧写入者，备份完整数据库、配置与启动信息。沿用原经验库与 scope，不新建空库假装升级成功。

历史经验、ID、修订、证据、查询能力必须保留。旧的冷却记录或 generated receipts 不能迁移成宿主已收到正文；新系统第一次相关触发允许重新交付。

已经有结构化反例但没有 cues 的旧条目：保留原有有效入口，暂映射到一个稳定的 `legacy_primary` 关联点。首次通过 lookup 返回完整紧凑正文，之后同一关联静默。没有经核实的短文本时，不自动从标题/前 N 字生成多关联点提醒。后续由有证据的经验修订补齐 cues。这是旧数据能力受限，不能静默禁用整个旧经验。

非结构化历史正文继续通过 search/read 访问，不批量包装成伪反例。已有 confirmed agreement reference 保留原来源身份，不能为它编造失败案例。本次不借经验升级扩大规范注入范围。

升级后协议文档不得残留“每轮一次查询预算”“冷却 10 分钟即重新要求调查”“read 即核实”等冲突描述。旧选项要明确弃用/拒绝，不保留隐藏回退路径。

| A39 | 新 cue 包含该版本正文没有的新风险事实 | 不能仅发短引用；需新经验或实质修订并首次交付正文 |
| A40 | 非阻塞短引用的实际传递 | 具体反例材料进入当前任务的模型继续请求；仅通知/日志或通用“请注意”不通过 |
| A41 | 自主拆解任务或进入下一步，没有新匹配/新 cue | 不追加记忆上下文，不产生“每任务一次”的提醒 |
| A42 | Agent 判断本次不适用或当前无问题，未发现新的可复用事实 | 无强制写回、无拒绝收据，不新增长期经验 |
| A43 | 核实后修订既有经验的边界 | 正文/cue/索引同步更新、保留历史；旧投递不能覆盖实质新版本 |

“重复 100 次”是压力测试输入，不是运行时计数策略。

真实宿主验收至少覆盖 A02～A07、A12/A13、A18/A20 与 A30/A31，分别报告：hook 实际执行、原生阻止生效、成功工具结果观察、非阻塞短线索可见。纯函数测试、模拟 stdin、数据库 receipt 不能替代真实宿主证据。

模型是否自主利用反例、是否出现错误锚定、是否重新调查过多，需要在相同任务/经验 fixture 上另做行为试验。报告观察与失败，不以“模型说已理解”验收。

行为试验同时包含历史风险仍存在、条件不适用和风险已被修复的对照案例。根据当前证据不采纳经验、保持正确实现，也是成功结果；不能用采纳率、修改次数、追加调查次数或复述提示作为成功指标。只凭无动作也不能证明 Agent 已思考，评估应看可观察证据与任务结果，不索取私有推理或新增运行时解释仪式。

## 13. 防退化审查：出现任一项即不符合本方案

| 退化实现 | 为什么不接受 |
| --- | --- |
| 每次命中都追加短引用，只是缩短了字数 | 上下文仍按工具次数线性增长 |
| 每个类/文件/工具各建一个 cue | 入口变化被伪装成新的风险关联 |
| 对正文取前 800/200/80 字作为短引用 | 截断不保证保留反例、条件和否定 |
| 首次 lookup 后 hook 再附一遍正文 | 同一信息走两条通道重复交付 |
| 用标题“注意回馈日志”替代具体历史线索 | 缺少可激发调查的反例事实 |
| Agent 判断不适用后仍要求调查、改代码或解释登记 | 把经验材料变成必须服从的规则 |
| 把新风险藏在已交付经验的新 cue 中，仅给短引用 | 绕过新经验首次稳定交付的约束 |
| 返回“应该修改某类/已经核实/无需调查” | MCP 越权替当前任务下判断 |
| 10 分钟、第 N 次、每轮一次决定提醒/调查 | 重新引入用户已否定的机械调度 |
| lookup 一次就放过整轮、整个类或全部候选 | E1 的交付掩盖未交付 E2 |
| generated response 直接等于宿主收到 | 传输失败会错误抑制首次曝光 |
| 依赖 Agent 自报已读、skip、complete | 重新依赖自觉并增加流程负担 |
| 安装一个额外总结 Agent/语义分类服务 | 改变已认可的责任分工和成本模型 |
| 全类依赖图传播、全工具全文扫描 | 关联范围失控，扩大 hook 开销 |
| 每轮重置、compact 后回灌所有正文 | 退回重复上下文膨胀 |
| 为保证模型“真的思考”增加 Stop gate | 恢复强制收尾整理流程 |
| 读写原始 transcript、保存完整业务工具返回 | 违反无原文采集约束 |
| 把查询/路径定位/代码哈希当适用性证明 | 机械证据被误当语义核实 |
| 用 SQLite 毫秒耗时声称端到端高效 | 忽略进程启动、模型生成和调查成本 |
| 把模型可见 additionalContext 当原位替换 | 公开接口的追加行为没有消失 |

实现代码审查与真实宿主结果都要对照此表。任何必要偏离应在实施报告中明确列出原因、影响和替代行为，不能以优化为名悄悄更改核心契约。

## 14. 实现交付要求

交付应包含源码与迁移、自动测试结果、实际宿主验证记录、修改后的协议文档、样例 lookup 正文、样例短引用，以及一段 A→重复 A→B→重复 B 的完整事件统计。

统计至少包括：实际 block 数、lookup 次数、各阶段追加内容字节数、cue 命中/合并/发出数、宿主回执成功/失败数及端到端耗时。日志仅保留必要元数据和隔离 fixture，不保存用户对话原文。

有源码与运行版本差异时先核对，不用旧版本覆盖已上线功能。源码同步、打包、安装或部署按后续实际实现任务及适用 AGENTS 执行；本文不是立即改动现有业务服务或上线数据库的操作命令。不要把嵌套 memory-mcp 仓库的本地宿主组件与父项目 VPS 业务服务混成一个部署目标。

以下能力不得仅凭文档宣布完成：实际宿主支持、success receipt 到达、模型可见短引用、上下文压缩后行为，以及 Agent 对反例的实际利用。没有验证的部分明确列为未验证。

## 15. 可直接交给实现模型的指令

> 请按本文实现“首次正文交付 + 按关联点增量提醒”。先核对工作树、已有草稿、实际运行版本和宿主回执能力，再按实施顺序修改。保护用户已有未提交修改。
>
> 核心语义不可退回：Agent 理解任务并主动 lookup；MCP 保存紧凑反例；hook 按真实投递记录与 cue 决定自动发送。相同关联跨工具静默，新关联只给固定短线索，不用时间/次数决定调查，不要求 Agent 报已读，不收集原文，不引入每轮提醒或 Stop 整理。
>
> 短线索必须作为具体反例材料进入 Agent 当前任务上下文，不得替换成泛泛的注意事项。Agent 根据当前证据判断经验不适用或当前实现没有问题，是允许的有效结果，不得强制采纳、制造修改或登记拒绝。
>
> 完成验收矩阵与真实宿主试用，按防退化表自查。报告实际实现、验证证据、成本变化和未验证边界，不能只提交一份新的架构说明或以模拟测试替代宿主验收。

## 16. 依据与协议核对入口

本方案的核心决策来自本次用户讨论；业务示例全部为假设。早期源码显示的问题是正文截取、通用流程材料、重复交付与交互打断等叠加；没有精确旧版运行记录，不能宣称已量化各因素占比。

Codex 公开协议说明了 PreToolUse 非阻塞 additionalContext 与 PostToolUse 工具结果字段。不同事件/工具有不同错误语义，实际安装版本仍需验证：[Codex Hooks](https://learn.chatgpt.com/docs/hooks)。

ZCode 公开协议说明了 pre/post 执行顺序、输入/输出与工具调用关联字段。不要把配置写入成功当成既有 session 已热更新：[ZCode 插件与 Hooks 文档](https://github.com/zai-org/zcode-plugins/blob/main/docs/PLUGIN_DEVELOPMENT_CN.md)。

其他宿主按各自真实适配器协议验证，不根据 Codex/ZCode 支持情况推断其他客户端也具备相同事件与回执。
