# 通用 hook 接入与业务验收

memory-mcp 为不同宿主 Agent 提供同一套项目记忆：记录用户明确的业务决策、约束和纠偏，保留原话与语境，在后续相关开发中检索和回读。宿主客户端负责事件交付，宿主模型负责业务理解；程序不内置模型。

把安装包交给当前宿主 Agent 阅读 README，由它识别实际运行环境并选择接入方式。用户不需要先判断自己属于哪个客户端，更不应逐轮输入记忆工具名。

## 1. 由宿主 Agent 自主识别与适配

按以下顺序执行，不根据模型名称推断客户端：

1. 识别实际客户端、版本和执行模式，以及程序和数据库实际运行的机器。桌面、远程执行器、容器和云端编排分别核对。
2. 运行安装包的 version、help、guide；识别已有安装、真实数据路径及当前业务项目的 scope。先备份配置与数据，不重建旧库。
3. 将 stdio MCP 合并到当前客户端的用户级配置，保留其他服务。实际调用 bootstrap、搜索和完整读取；配置存在不代表当前会话已加载。
4. 核对该客户端官方 hook 文档及本版本支持能力，选择已实现适配器，或在用户级位置实现并验证宿主原生适配。不能把其他客户端的事件名、JSON 或配置路径直接套用，也不能冒用其他 host 参数。
5. 真实验证事件输入、项目路由、记忆存取、材料交付和业务使用。保留宿主的信任、授权和新会话步骤，未验证的能力标为未知。

内置安装器只是减少已支持宿主的接入工作，不定义本工具可以被哪些 Agent 使用。其他支持 stdio MCP 的 Agent 仍可使用通用记忆工具。内置 hook 适配器缺失时，不得把通用 MCP 已连接说成自动 hook 已生效。

不得修改项目 AGENTS.md、CLAUDE.md、项目规则或项目 hook 配置。适配脚本、项目注册信息和诊断状态放用户级目录；只修改本程序拥有的配置项，不覆盖其他插件或 hook。

## 2. 按实际能力接入

| 宿主能力 | 可实现的流程 | 验证重点 |
| --- | --- | --- |
| 输入事件交付原文，且支持模型上下文输出 | 输入时采集原文并检索相关案例，向本轮交付有上限的材料 | 检查真实事件、检索回执与模型实际收到的内容 |
| 工具前事件交付工具名和资源路径 | 进入新变更范围时补查，避免只在开工时读取一次 | 检查时机、去重和自身记忆调用不递归触发 |
| 回合结束事件支持主模型继续执行并使用 MCP | 请求宿主判断是否有业务决定或纠偏，保存案例或修订，再留下处理回执 | 普通聊天可跳过；语义处理须有真实存取结果，继续次数受限并说明模型开销 |
| 只支持事件采集，不支持语义处理或材料交付 | 仅报告实际完成的采集能力 | 不将原始聊天写入声称已整理的业务偏好 |
| 只有会话启动 hook | 可提供启动软引导 | 不声称覆盖了中途反馈、纠偏和后续决策 |
| 无可用 hook | 仍可通过 MCP 查询、保存和修订 | 明确自动触发尚未接通，不让用户误以为已启用 |

事件名称和输入输出格式由各宿主适配，不作为通用协议硬编码给所有 Agent。普通命令 hook 本身没有可调用宿主模型的对象；需要理解业务时，使用该宿主确实支持的模型处理机制，并如实说明额外回合或预算。

## 3. 当前内置适配器与其他宿主

| 客户端／模式 | 当前实现状态 | 接入入口 |
| --- | --- | --- |
| ZCode 本地进程 hooks | 已有原生 Go setup/hook/doctor 候选；完整语义整理仍需真实客户端验收 | [ZCode 适配说明](adapters/ZCODE.md) |
| Codex 本地客户端 | 通用 stdio MCP 可接；本包尚无 Codex hook 安装适配器 | 按 README 注册 MCP；宿主 Agent 核对其版本官方文档后，单独实现并验证用户级适配，不冒用 --host zcode |
| 其他支持 stdio MCP 的宿主 | 通用核心可接；hook 能力按客户端实测 | 由宿主 Agent 依据官方文档完成原生接入，明确已验证范围 |
| 托管云端编排 | 事件与工具挂载取决于平台支持 | 不能用容器里的 CLI 配置证明云端宿主已加载；按实际平台入口核对 |
| 仅支持远程 HTTP MCP 的宿主 | 本包仅提供 stdio，不能直接连接 | 报告传输限制，不伪造本地连接成功 |

setup 和 hook 必须显式指定真实 --host。当前内置值只有 zcode；它只是适配器能力清单，不是对通用记忆核心的客户端限制。

## 4. 共同的业务处理原则

- 先确定项目范围再检索。保留已有 scope，同名不同仓库不合并，未知范围不默认写入 global。
- 用户输入时，根据当前任务及实际资源查找相关业务案例；短句“继续”应结合已有任务主题，不能只搜索这两个字。
- 原始输入与宿主实际交付的答复是来源，不等于已确认的业务结论。普通搜索应避免把原始聊天当成业务决定；宿主仅保存实际值得复用的案例。
- 业务案例正文自由表达，保留用户原话、语境、适用范围和不确定性。结构字段只追踪来源、项目和版本，不确认语义正确。
- 纠偏先查已有决定，修订当前案例，保留旧版和反例，不用新建一条相反规则掩盖旧版。
- 交付的是本次相关材料，明确来源、版本及截断状态。重要判断回查全文；没有匹配就报告没有材料，不拿无关近期记忆填充。
- 失败、中断或未完成整理保持可见，不把收到事件、请求了模型或写入回执说成业务理解正确。

## 5. 真实业务验收

在独立测试项目、scope 和数据目录中完成；保留正式连接及原数据，避免两个同类 hook 重复处理输入。配置后按客户端要求新建会话。

1. 自然表达一条业务决定，例如：“日期安排详情和编辑归在安排模块，不增加一级菜单。按这个原则给我一版方案。” 不输入记忆工具名。检查实际案例是否包含原话、背景和来源。
2. 新会话提出相关开发任务：“给日期安排新增编辑页，怎么安排入口？” 检查是否在制定方案前召回前述案例，以及模型是否正确理解适用范围。
3. 再提出纠偏：“独立业务域可以新增一级入口，详情和编辑仍不单独增加。” 检查是否修订原案例、保留旧原文，后续是否使用修订版。
4. 检查不相关任务、普通聊天、切换项目和资源范围扩大，分别观察无关记忆干扰、强行生成偏好、串项目及补查遗漏。

分别记录：配置写入、事件到达、实际存取、材料交付、案例整理、后续业务正确使用。固定答案探针只能证明通路，不能代替业务验收。保存脱敏事件样本、客户端版本和运行模式；模型自述仅是证据的一部分。

## 6. 分发给其他 Agent 的开场白

> 请阅读安装包 README，按 docs/HOOK_SETUP.md 自主识别当前客户端、版本、运行模式和业务项目，复用原记忆数据与 scope。备份并保留用户配置，只使用已验证的宿主能力完成用户级接入，不修改项目规则。优先选用已实现的适配器；缺少适配器时依据该宿主官方文档验证原生方案，不套用其他客户端配置。分别报告 MCP 连接、hook 触发、案例整理和后续业务检索的实际结果。
