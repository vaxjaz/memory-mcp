# Install or upgrade memory-mcp 0.6.4

This offline bundle contains platform archives, the exact source, `SOURCE_COMMIT`, inner checksums and the agent guides under `docs/`. Verify the outer archive against the release checksum when available. Select the platform archive and use `build-info` to verify its version, schema and full source commit.

The agent should execute the requested upgrade using the bundled `docs/AGENT_INSTALL.md`. The `docs/AGENT_GUIDE.md` guide is also available inside each platform archive and through `memory-mcp guide`, and `docs/API.md` lists every tool, parameter and command. Identify the real client, service, original library and verified scope. Stop all old writers, save a complete pre-upgrade backup and keep the old executable. Preview the schema with `migrate` and automatically apply the supported conversion with `--apply --backup` when required. Convert legacy tool registrations into the one `tool-probes.json`, run setup again from the new executable for every bound project (the client launches the hooks by the path setup wrote, so replacing the executable alone leaves them on the old program), read `unreachable_cues` in the doctor report, and reconnect the actual client.

0.6.4 upgrades the write judgment and the scan decision, not just the storage schema: bodies are two exclusive forms (fact, or pitfall plus counterexample), authored cue text is rejected at the write boundary, and a write that cites the same evidence as a same-project record, shares an entrance with it, or states a body overlapping it by half returns `needs_comparison` with a prefilled `resolution_template` (fill `action` and `difference`, resend the same draft and request_id). A cue that no tool rule of the project could ever fire is refused with nothing written; `doctor` lists stored cues of that kind as `unreachable_cues`. All tool rules live in one `tool-probes.json`: `tools` for every project, written and completed by setup, and `projects` for one project. `doctor --out FILE` keeps large reports out of truncated tool output, reports hooks that still launch another program, and lists any `*.pre-schema8` probe leftovers with the conversion table in the install guide as the remediation path. The guide's Function model section names the runtime functions — `W(x)` write judgment and `R(x, M)` recall (this release's changes), `F(j, E, m)` hot fusion and `P` verification budget.

Before activating the migrated cues, audit the existing records with the original scope and follow the full inventory cursor. Trace each rule through the project's existing implementation. Verify its behavior with tests, an isolated replay or the relevant historical code revision. Use business sources to establish domain intent and scope. **Semantic distillation of stored records is prohibited.** The old text locates a case. The evidence determines its revised rule and trigger. For a first installation, follow the default historical-code initialization in the same guide.

For duplicate consolidation or archival, show the exact affected IDs and retained evidence in a cleanup preview. Apply it only after fresh user approval. Summarize the result in a few lines with the installed version, migration counts, concrete verified trigger examples and outstanding decisions. If verification fails, restore the stopped service's old executable, configuration and full backup together.
