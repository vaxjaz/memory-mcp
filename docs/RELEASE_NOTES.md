# memory-mcp 0.6.4

- Experience bodies take one of two mutually exclusive forms: a sourced business `fact` with its object/environment/time qualifiers inside the sentence, or `pitfall` + `counterexample`. `impact`/`applicability`/`boundary` become optional legacy columns; submissions that fill them beside a fact are rejected with the field position. Authored cue text is rejected at the write boundary, first lookup and reminders quote this version's body only, and a pure alias revision inherits the unchanged historical cue text without forking the version.
- W(x), comparison before a write: the write path judges a new observation against same-project records that cite the same evidence locator, share an entrance, or state a body whose shared words are at least half of the distinct words of both together. Sharing common words alone no longer starts a comparison (on the reference library this cut the compared records from 23 of 24 to 4, all related). A hit returns `needs_comparison` with zero writes, the current facts of the candidates, match reasons, a paging cursor over the full list and a prefilled `resolution_template`. The same draft and request_id resubmitted with `resolution.action` commits the judged relation — `reuse` (current ID), `supplement` (independent source joins the root, claim unchanged), `revise` (complete new version), `create` (new root; target never a previous_id), `defer` (nothing written). Targets must be candidates this comparison showed and still current; the final candidate recheck runs inside the write transaction so concurrent paraphrases yield one root; committed actions and targets are persisted per request and re-deciding conflicts.
- W(x), cues that could never fire: a cue naming a tool no rule registers, a field no enabled rule exposes, or a result nothing observes is refused with nothing written; the error gives the position, the reason and what to register. `doctor` lists stored cues of that kind as `unreachable_cues`, so an upgrade shows which cues stopped being able to fire.
- R(x), one file of tool rules: `tool-probes.json` in the data directory is the single source. `tools` applies to every project and `setup` writes the default rules into it on first install and adds any default rule that is missing on upgrade, never editing a rule that is there; `projects` holds a project's rules and overrides `tools` by tool name. There is no separate built-in set: what will be scanned is visible in the file and in `doctor` as `probe_surface`. Rules select a native tool with `tool` or an MCP tool by its bare name with `mcp_tool`, map cue field names to input paths including array elements (`questions.*.question`, `questions.0.question`), and list in `scan` the command names a shell rule reads. Write and Edit are listed with `"enabled": false`: every routed tool starts a hook process on each call, so a project switches on the writing tools it needs.
- R(x), what a call carries: each field of a tool call is judged on its own against the bound project root — a path outside the project, an unexpanded `~` or `$VAR` path, an instruction file, an oversized value or a missing field leaves the other fields in play — and every verdict has a name. A call that reached the hook but was not scanned is recorded in `doctor --session` as `probe_skipped` with its outcome (`tool_disabled`, `operation_not_scanned`, `instruction_file`, `no_eligible_text`, `path_outside_project`, `path_unresolved`, …) and without the argument values. A Read of a file outside the session directory — a sibling module of the same project — used to be judged outside the project and skipped without a trace; it is now judged against the bound project root and, when a call is skipped, leaves a trace with a named outcome. A cue condition on a named field now compares every value under that name, so one array element cannot hide behind another.
- R(x), lookup: a term with no searchable lexical form — a single Han character, a version number like `0.6.4` — is dropped and reported in `dropped_terms` instead of failing the whole call; a query fails only when all of its terms are dropped.
- Diagnostics: `doctor` reports `split_executables` and clears `configuration_consistent` when the hooks still launch another program than the MCP service, which is what a partial upgrade leaves behind; it adds `probe_surface`, `unreachable_cues` and the `probe_skipped` rows, writes the full JSON report with `--out FILE` (stdout keeps only the path, immune to host output truncation) and flags `*.pre-schema8` probe leftovers with explicit re-registration guidance. `memory-mcp <command> --help` lists the parameters of that command alone and a parameter of another command is an error instead of being ignored.
- Messages an agent can act on: a rejected call names the parameter as the reference spells it (`experience.cues is required`, `operations[].entry_id must be string`); a project that is unbound, or bound to another scope, is reported with the directory, both scopes and the way out; a code evidence path that does not exist is reported with its position and the path; the title is checked before a write can ask for a comparison. `doctor --probe` names the rule really in effect (`tools`, `project` or `default`) instead of always `tools`. `setup` refuses a `--data-dir` other than the library the service already uses and says which one that is.
- The rules file lists one rule per line (41 default rules in 88 lines, the long command list wrapped), and the hook event log keeps its newest 20,000 rows.
- Maintenance: every `memory_cleanup` parameter says when it is used, and each wrong step — a missing or unknown `plan_id`, `apply` before approval, `undo` before `apply`, a `purpose` that does not fit the plan's state, a reminder policy change without a prior `confirm` — is refused with one sentence naming what is missing and the next step. The reminder interval stays at 100 stored experiences by default and is changed by `confirm` with `purpose: "configure"` followed by `configure`.
- Reference: [API.md](API.md) lists every tool with its signature, every parameter with its type, required mark and meaning, the return fields, the hook events, every command and its flags, and the `tool-probes.json` keys. The acceptance suite reads the program's own schemas and help output and fails on any difference. [CAPABILITY_MATRIX.md](CAPABILITY_MATRIX.md) states what is supported and how each item was verified.
- Schema 10: older binaries refuse to open the new library instead of silently dropping the fact form; `migrate --apply --backup FILE` upgrades schema 9 (0.6.3, dev.11–dev.13) with a rollback baseline and inventories legacy narrative qualifiers, cue facts beyond the body and records missing evidence. Committed request retries replay their original outcome and accept the rebuilt dev.3 fingerprint; replays pass the current project binding before the historical receipt.
- Packaging refuses uncommitted changes so `SOURCE_COMMIT` always matches the built tree unless `--allow-dirty` is explicit. The distribution workflow verifies protocol behavior with the target tag's own scripts and keeps version/checksum identity in tooling. `python scripts/acceptance.py` runs every gate with one command: build, vet, Go tests, packaging and release unit tests, and the protocol, recall, upgrade and user-scenario scripts. A gate that excuses itself is reported as SKIP, never as PASS, and the capability matrix's overview is checked against its own rows.

This release uses integration protocol 13 and schema 10. Clients and hooks must both run this version: after replacing the executable, run `setup` again for each bound project.

# memory-mcp 0.6.3

- Configure built-in and project tools through one registration path. Bind keyword matching, optional `when` prerequisites and verified earlier tool results to the cue.
- Require a reusable future decision and an exact supporting evidence reference for every experience write or revision.
- Request lookup once per challenge. Covered retries can proceed while confirmation is pending. Inspect the receipt stage with `doctor --challenge FULL_ID`.
- Continue historical search and cleanup inventory through legacy IDs and timestamps using the returned cursor.
- Include the installation, upgrade and agent guides in the offline bundle and each platform archive. Agents initialize from verified project history and recheck stored rules against project code before activation. Duplicate consolidation and archival use a user-approved cleanup preview.

This release uses integration protocol 11 and schema 9. Back up the original library and run the packaged migration steps before opening an older schema. Libraries already on schema 9 can open directly. Keep the existing scope, library and wakeup policy during setup.
