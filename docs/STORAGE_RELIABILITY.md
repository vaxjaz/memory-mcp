# 存取可靠性与升级边界

本文描述 v0.1.2 的可靠性增强。旧版 v0.1.1 不含这些增强；以实际程序的
`help`、bootstrap 的 `schema_version` / `features` 和返回字段为准。
本阶段只改进持久化、传输和结果遍历，不自动整理、归纳或重写用户记忆。

## 写入与重试

新增可选 `request_id`，由调用方为一次逻辑写入生成唯一值，例如 UUID。

- 同一 scope、同一 ID、相同内容与修订目标重试，返回同一个原始记录 ID。
- 同一个 ID 用于不同内容或不同 previous_id，明确返回冲突，不静默覆盖。
- 修订的请求 ID 放在 `draft.request_id`，重试仍使用原 previous_id。
- 新纠正使用新的请求 ID。两次独立但文字相同的反馈不会自动合并。
- 请求键与记录、来源链接在同一事务提交，重启后仍有效；忘记整条记录时一同删除。
- 没有传入 request_id 的旧调用继续可用，但不具备重试去重保证。

写入和读取都返回 UTF-8 正文的 `body_bytes` 与 `body_sha256`，便于比较写前与读后内容。
原文的换行、空格与 Unicode 不做压缩或规范化；非法 UTF-8 明确拒绝。
校验摘要不能证明用户原意或内容真实性，也不是防篡改签名。

每个物理数据库连接都设置外键、busy timeout、WAL 和 synchronous=FULL，
连接被池替换时仍生效。数据库事务成功后才返回成功。遇到响应丢失或取消时，
调用方仍应使用同一个请求 ID 重试，不能由未收到响应推断没有落盘。

## 读取与结果遍历

- memory_read 返回指定版本的完整正文、来源和当前版本定位；旧正文不会被修订覆盖。
- memory_search 返回有限摘录，`has_more=true` 时提供 `next_cursor`。
  继续查询时传入 `cursor`，保留原 scope、query、kind、include_global。
- 入站引用超过一页时返回 `references_has_more` 与 `references_next_cursor`；
  以同一记录 ID 和 `reference_cursor` 继续，避免反例在前 100 条之外被静默截断。
- 游标关联查询条件，不能用项目 A 的分页状态继续读取项目 B。
- 分页采用键集定位，稳定数据下不会因相同时间戳或前一页数量发生重复、漏页。
  多次调用之间仍是实时数据：并发修订可能改变当前版本集合，不宣称全程冻结快照。
- 关键词检索仍是字面匹配。完整遍历结果不等于语义检索完备，更不等于判断正确。

## 一致性备份

源码版本新增：

```sh
memory-mcp backup --out /absolute/path/snapshot.db --data-dir /path/to/data
```

它通过 SQLite VACUUM INTO 生成独立的一致性数据库，包含 WAL 中已提交的数据、
历史、来源关联与重试键。备份期间不需要复制正在变化的 WAL 文件。
输出通过同目录临时文件和不覆盖的原子链接发布；文件系统不支持时会明确失败。
目标已存在就失败，不替换旧备份。

恢复时关闭所有使用该数据目录的进程，把完整备份作为目标目录的 memory.db，
不要与另一份数据库的 WAL / SHM 混用。恢复前保留原目录。
JSON export 仍用于审计和查看，没有 JSON 导入命令；恢复完整状态应使用数据库备份。

## 数据库版本升级

数据库 v1 升到 v2 只新增重试请求表及版本标记，不重写既有正文、ID、历史与来源。
升级前关闭旧进程并备份整个数据目录。旧版程序会拒绝打开 v2 数据库，不能直接降级；
如需回退，应恢复升级前的 v1 备份。多个客户端共享库时应一同升级。
后续内容整理应另行设计，不与这次存储结构升级混在一起。

## 验证范围

自动化验证覆盖：

- 原文写入、回读与摘要一致；重启后按请求 ID 重试不新增记录。
- 修订请求重复送达与冲突检测，旧版本和反例保持可读。
- 超过单页的中文检索与入站引用，以及项目范围和游标不匹配。
- 数据库连接更换后仍启用外键与同步配置。
- 多个独立进程写同一目录、收到成功响应后强制结束进程再恢复读取。
- v1 结构升级后原有记录及关联不变。
- 备份恢复保留正文、来源和重试键；另一写事务未提交时备份只包含已提交数据。
- MCP 实际调用、stdio 进程重启与完整工具返回值。

这些验证证明已测试环境中的行为，不覆盖硬件断电、所有文件系统或所有宿主的
上下文截断方式。真实跨平台运行与长期数据使用仍需继续观测。
