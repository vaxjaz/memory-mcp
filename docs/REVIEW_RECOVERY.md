# v0.2.1：纠错通道与检索修复

这些修复首先以 v0.2.1-reviewfix.1 单独提供，现已包含在 v0.2.2-adapters.2 中。数据库仍为 v3，不批量清标记、不改写历史正文。安装升级继续遵循 [AGENT_INSTALL.md](AGENT_INSTALL.md)，复用原库和项目绑定。

## 待复查不等于禁止纠错

旧程序对 supports、contradicts、context 一律要求来源已复查，导致连“反驳这条待核结论”的真实记录也无法关联。现在分别处理：

| 操作 | 规则 |
| --- | --- |
| supports | 必须引用当前、活动且没有 needs_review 的来源。失败说明来源 ID、当前修订及处理方向 |
| contradicts / context | 允许关联待复查、历史及非活动条目，保留原编号；引用不代表其有效，更不会替它清除警告 |
| 保存事实更正 record | 可以记录实际新事实并引用被纠错条目，不要求先恢复旧结论 |
| 新增或修订 case/hypothesis | 仍需有效的 record/case 作为支持或来源语境；仅有待复查背景或被反驳对象不够，不能靠换关联名洗成有效结论 |

既有客户端用 context 连接实际用户原文的习惯保留：当前有效的原文可提供出处，但语境引用不验证内容本身。普通派生材料仍须通过准入条件及相关上下文检查。旧资料可继续读取，不强制回填新 profile。

## 两种恢复方式

**结论要改：直接 revise。** 读取目标当前版本和新依据，previous_id 指向待复查目标；完整正文写清修正，supports 指向有效新依据。可以用 context/contradicts 保留被纠错旧内容的定位。无须先 recheck，不要求为同一事项另建案例。旧版本与警告保留，新版本只有满足来源要求才能写入。

**结论不变：recheck 预览后确认。** source_ids 提交每个关联来源的有效当前版本，包含背景/反驳对象的阅读确认。待复查的 supports 上游必须先修订/复查；弱引用可保留警告，但不能成为唯一有效依据。新预览提前检查，不让用户批准明显不能执行的复查。错误列出目标、阻塞上游、缺失或多余 ID；不能把目标自身随意当成依据。

多层链可以用 `memory_cleanup(action=preview, operations=[上游recheck, 下游recheck])`，按依赖顺序提出一个具体计划。预览只在内存中验证这个顺序，不清标记、不制造更正案例。展示计划、得到新的用户确认后，apply 在同一事务执行；任何失败都回滚。来源在预览后变化仍会使旧计划失效。
确认先后使用数据库内的持久操作顺序，避免 Windows 同一时间戳、时钟回拨或 RFC3339 小数位差异造成误判。预览前已写入的旧消息即使时间显示得更晚也不能批准新计划；预览后真正新写入的确认可在物理时间戳相同时通过。撤销也必须使用执行后新写入的确认。来源和摘录校验、宿主确认实际用户意图的责任不变。
旧库补齐 v3 兼容元数据，不改正文、不清标记；升级前仍须备份并停用旧实例。旧待确认计划没有顺序信息时保留严格时间校验，无法判定就重新展示预览并取得新确认，不能自动放行。

背景及反证的未来变化仍会传播复查提示，避免丢失后续纠偏；“允许引用”与“是否需要再读”是不同问题。清洗确认和备份/撤销规则保留。

## 超过 8 个检索词

原来 memory_context 与底层 search 各有一个 8 词硬限制。现在去掉词数限制，按空白拆分、忽略重复词，保留全部不同线索；中文、大小写去重和字面 OR 查询不需要模型或网络。

- `memory_context prepare` 的 `keyword_search.status=searched` 表示实际搜索；used_terms/query 是实际使用内容，没有截掉第 9 个及后面的词。
- 去重后查询总长度最多 2048 字节，原始整理输入最多 65536 字节，约束资源开销。超过时 prepare 仍返回分页目录，状态为 directory_only，并明确关键词搜索没有执行；宿主应结合目录缩小线索，不能声称无相关记忆。
- `memory_search` 的直接查询仍要求总长度合规，返回具体长度错误。分页继续使用相同查询语义，不丢后续结果。SQL 使用有界 JSON 参数，避免词数增长撞上 SQL 表达式或参数数量限制。

验证覆盖真实编译程序经 stdio MCP 的纠错记录、待复查目标直接修订、复查预览/确认/恢复链和超 8 词搜索；宿主业务判断仍需要实战验证。
