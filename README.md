# memory-mcp

Stable release 0.6.4 judges new observations against similar history inside the write path and supports [project-specific tool probes](docs/AGENT_INSTALL.md#register-a-custom-tool).

Local verified-experience memory. The host understands the current task, constructs queries and judges applicability. MCP stores compact counterexamples and performs local retrieval; it never calls another model.

Seven tools: memory_bootstrap, memory_experience_record, memory_reference_record, memory_experience_lookup, memory_search, memory_read, memory_cleanup.

Specific observed entrances map to stable, evidenced associations (cues). An undelivered experience requests one lookup through a real challenge. Only the actual successful native result credits the returned bodies and its trigger cues. Later entrances for the same cue are silent; a different undelivered association emits one bounded fact of this version's body while allowing the operation. Another experience still requires its own body. New turns do not reset delivery. There is no global lookup permit, cooldown, model-authored acknowledgement, per-turn experience reminder, raw transcript capture, async write or Stop continuation.

Lookup returns one JSON text copy of complete facts, conditions, exceptions and evidence within 8 KiB, with pagination. Index/entrance metadata stays out of the visible experience DTO. Voluntary lookup/read remains available. Delivery records describe system output, never understanding, applicability, authorization or an obligation to change code. Finding no current problem is a valid result.

Version 0.6.4 uses integration protocol 13 and schema 10. Libraries with an older schema use the [upgrade procedure](docs/AGENT_INSTALL.md#upgrade-to-the-cue-schema) before setup; after replacing the executable, run setup again for each bound project so the hooks and the service run the same program. Experience bodies take one of two forms: a sourced business fact with its qualifiers inside the sentence, or pitfall plus counterexample; authored cue text is retired at the write boundary. The write path itself compares a new record with same-project records that cite the same evidence, share an entrance, or state a body overlapping by at least half: a hit returns needs_comparison with a prefilled resolution_template and zero writes, and the same draft resubmitted with resolution.action (reuse, supplement, revise, create, defer) commits the judged relation; concurrent paraphrases converge to one root through an in-transaction recheck. A cue that no tool rule of the project could ever fire is refused with nothing written.

Which tool calls are scanned is decided by one file, tool-probes.json in the data directory: setup writes the default rules into it, projects override or extend them, and doctor shows the rule in effect for each tool and why a call was not scanned. The common database query tools, including ZCode's mysql_query, find their query fields automatically. doctor writes full reports with --out, reports hooks that still launch another program, lists the cues that can no longer fire, and flags pre-schema8 probe leftovers. Lookup delivery diagnostics distinguish generated, observed and missing results.

Agents initialize a first installation from verified project code and business history. On upgrade, they back up the original library, run the supported format conversion and recheck existing rules against project code. Duplicate consolidation and archival require explicit approval of the cleanup preview. See [first install](docs/AGENT_INSTALL.md#first-install) and [upgrade](docs/AGENT_INSTALL.md#upgrade-to-the-cue-schema).
